## Proposed destination set

| Destination | Identity and opening policy | Purpose |
| --- | --- | --- |
| `app-terminal` | All root terminal instances share this destination. Open restores an instance or opens the ordinary Terminal when dormant. New window uses the existing shell request, within its four-instance limit. | This exercises multiple instances, stacks and creation limits. |
| `app-files` | The Files application is a singleton destination with its existing browse state. | This exercises dormant opening and singleton restore without resetting navigation. |
| `app-editor` | The Editor application is a singleton destination. It retains its open tabs and unsaved buffers. | This exercises close vetoes and preserves application identity. |
| `settings` | The Settings root is a singleton destination. | This provides a lightweight control case. |
| `article-coincidences` | The exact public article at `/page/coincidences` is a document destination. | This distinguishes a document pin from a generic reader or editor pin. |
| Role-filtered tools | Account and staff destinations are registered only when the current server-rendered capability set permits them. | This exercises account changes and denied operations. |

The public catalog can later supply further article registrations through the same explicit metadata path. External links, framed sites, tag lists and child image windows are excluded from the first integration. Book-level and chapter-level pin identity need separate policy before adoption; the existing Pins bar already stores chapter state and must not be silently flattened. An Editor file tab is not a separate root window, so the application pin must not be advertised as reopening a particular file.

The server should emit destination identity explicitly for initial root windows and `/window/{key}` fragments. Both render through `_Window.cshtml`, but their models are populated through separate paths. Numbered Terminal copies must receive the same application identity from the content model. The adapter must not infer association from titles, icons or a regular expression over generated instance keys. Dynamic replacement, rekey and book navigation must preserve or update explicit identity according to the final contract.

## Host constraints

The beta desktop uses a full-width taskbar below the launcher/workspace split. It fetches window fragments from `/window/{key}`; applet startup can finish later than fragment insertion. Terminal and Editor have deferred initialization. A completed window fetch must not be confused with an applet becoming ready. The frozen contract must identify which milestone settles a pending taskbar request, including failure and cancellation.

The launcher preserves native modified and new-context links, accepts destinations synchronously through `pudlLauncher.activated`, and uses shared feedback before popup dismissal. A phone changes its pinned presentation after that interval so the opened window becomes visible. Taskbar opening must respect that host layout policy without automatically reopening or focusing the launcher.

The existing `window-bar.js` inserts picture icons into generated running tabs. Dormant destinations have no source window. The candidate needs a documented image contract or an agreed shared-glyph fallback before the adapter can cover dormant, running, stacked and overflow entries consistently. Generated taskbar markup must not become a new integration API.

The current Pins resident applet and top-bar toolbar remain in place during the first candidate build. Their guest and account records include article and chapter identity, while taskbar preferences also need combined order. Taskbar preferences will use a separate versioned record, browser-local for guests and account-scoped for authenticated readers. Existing pins will not be migrated, deleted or duplicated automatically. Signed-in writes must use the site's authentication and antiforgery conventions, and temporary permission filtering must not overwrite stored unavailable IDs.

Server-rendered launcher entries already apply role and stage filtering through SiteMenu. Activation must revalidate capabilities and retain endpoint authorization; registration is not a security boundary. Creating a new instance and restoring an existing usable instance require separate availability decisions. Session expiry must clear pending state and leave retry or unpin available without exposing a different account's preferences.

The host's `pc-windows` persistence whitelist currently omits `z.order` and taskbar-order parameters. The integration must preserve supported layout URL fields while keeping persistent pin preferences separate from shareable window state. This needs a bare-visit restoration check in addition to explicit-URL reload tests.

## Pin eligibility correction requested on 7 November

Paul rejected a per-destination allowlist after articles other than Coincidences lacked the pin command in Firefox and Edge. Pinning must be available by default for reopenable windows, with an explicit opt-out. Host policies should cover categories such as articles and applets, rather than require an entry for each article or application. Stable destination identity and reopening metadata are still necessary for persistence, but supplying that metadata must not constitute individual permission to pin.

The current hardcoded registry does not meet this requirement. Expanding it with more individually registered articles is superseded.
